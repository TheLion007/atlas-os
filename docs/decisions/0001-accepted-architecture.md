# ADR 0001 — Accepted architecture and resolutions

- **Status:** Accepted (2026-09-21)
- **Sources:** Claude Design blueprint v0.1 (not included in this repository), the implementation master prompt, the Phase 1 audit.
- **Priority order when sources disagree:** blueprint → implementation prompt → existing repository → engineering judgement.

## 1. Decisions taken by the product owner

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                 |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| U1  | **Data layer:** hosted Supabase (PostgreSQL + Auth + Storage) is primary. Local Supabase via Docker for development. PostgreSQL stays the database architecture.                                                                                                                                                                                                                                                         |
| U2  | **Portability:** JSON export/import is a first-class feature so project data stays portable.                                                                                                                                                                                                                                                                                                                             |
| U3  | **Local-first spirit:** followed where practical (read cache, exportable data, pure client-runnable engine) without building an offline sync engine in v1.                                                                                                                                                                                                                                                               |
| U4  | **Repository:** `E:\atlas-os`, fresh `main` branch. GitHub remote to be connected later. **Nothing is pushed unless explicitly requested.**                                                                                                                                                                                                                                                                              |
| U5  | **Blueprint:** the original design deck was the canonical design reference; it is not included in the public repository.                                                                                                                                                                                                                                                                                                 |
| U6  | Atlas OS is the product name. Dorsel is seed/demo data, not product scope. Location is a generic first-class entity. The map is a real-world globe. Progress is derived, never stored. Graph edges are the source of truth for relationships. Financial data has a separate `dataKind` axis. Derived values are never stored. The Graph is the signature experience. The system supports projects anywhere in the world. |

## 2b. Implementation-time deviations (Phase 3)

These change something the Phase 1 audit proposed. They are recorded here rather than left implicit.

| #   | Audit proposal                                              | What was built, and why                                                                                                                                                                                                                                                                                                                                                                                                         |
| --- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R14 | Drizzle ORM for typed queries                               | **Not used.** Parameterised SQL behind a small `Db` interface. The constraints, triggers and RLS live in SQL migrations, so an ORM schema would be a second, drift-prone copy of ~20 tables. Detail writes are generated from the Zod schemas' keys (an allow-list, not request input) and reads use `to_jsonb`, so adding a field touches the migration and the Zod schema only. Revisit if query volume makes an ORM pay off. |
| R15 | RLS as defence in depth behind explicit `owner_id` scoping  | RLS is the **primary** isolation mechanism: every request runs in a transaction that switches to the `authenticated` role with the owner's id (`asOwner`). The server's own queries carry no owner filter, so a mistake there cannot leak data, and a mutation test proves removing the role switch fails 6 isolation tests.                                                                                                    |
| R16 | Supabase Auth session resolves the owner                    | Staged. The API is **deny-by-default** (401). A development-only `ATLAS_DEV_OWNER_ID` bypass exists, is ignored when `NODE_ENV=production`, and is verified over real HTTP. The Supabase session resolver lands with the login screen (Phase 4) and cannot be exercised without a hosted project.                                                                                                                               |
| R17 | API shape from the blueprint (`GET/POST /objects`, `PATCH`) | Additions the blueprint omits but relations require: `DELETE /api/objects/:id`, `POST /api/edges`, `DELETE /api/edges/:id`; `POST /api/objects` accepts `relations` so an object and its edges (e.g. a project and its location) are created atomically. `GET /api/objects` returns details only when filtered to one `type`.                                                                                                   |

### Phase 4 decisions (shell and design system)

| #   | Decision                                                                                                                                                                                                                                                                                                             |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R18 | **Demo mode is development-only.** The UI runs on illustrative fixtures behind one `AtlasDataSource` interface; fixtures are dynamically imported behind a `NODE_ENV` check and a demo session is impossible in production. Production stays deny-by-default (`/login` says there is no provider yet; no fake form). |
| R19 | **The object-type palette is muted and cool** (chroma ≤ 0.06, never warm or green), found by constrained search and enforced by tests. Sand is one element per screen; status colour marks marks, not small text (critical on surface is 4.43:1).                                                                    |
| R20 | **Only schedulable work can be blocked** (project, sub-project, task, milestone, decision). A `depends_on` between estimates is a data dependency, not a precedence. Found by looking at the first rendering: an actual figure was "blocked" by an assumption.                                                       |
| R21 | **The map draws a coordinate plane, not geography.** Real coordinates, equal scale on both axes, clusters for overlaps; the basemap is a separate provider in the Map phase. Objects at a place with no coordinates are listed, never plotted.                                                                       |
| R22 | **Graph selection outlives the peek panel.** Selection lives in the URL when the panel is open and locally otherwise, so dismissing the modal sheet on small screens does not deselect (found by the real-browser run: path mode was unreachable on tablet).                                                         |
| R23 | **Read endpoints added for the lenses:** `GET /api/graph`, `/api/activity`, `/api/settings` (read-only, owner-isolated, tested). Settings writes and FX entry arrive with Finance.                                                                                                                                   |

**Known gap:** the production `postgres` adapter (`src/server/db/postgres.ts`) is about 30 lines and has not been run against a real server (no Docker and no hosted project were available). Everything above it runs against PGlite. Verify it first when local Supabase or a hosted project exists.

## 3. Additional findings from the detailed design pass

| #   | Finding                                                                                                                 | Resolution                                                                                                                                                                                                              |
| --- | ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F1  | Deck slide 7 uses an edge called `influences`, which is **not** one of the six edge types on slide 6.                   | Modelled as `DEPENDS_ON` (the dependent milestone slips forward with lag). No seventh edge type.                                                                                                                        |
| F2  | Deck slide 7's example has _Relocation 2029 Q1_ downstream of _Purchase date 2031 Q2_, i.e. an effect before its cause. | The example is illustrative. Seed data uses a temporally coherent chain. The Relocation milestone must not precede what it depends on, and the engine flags such a schedule as a conflict.                              |
| F3  | Deck has both a spine `status` and a Task `state`.                                                                      | One lifecycle `status` (`draft · active · done · dropped`). "Blocked" is **derived** from `DEPENDS_ON` edges (the deck says blocked propagates as a warning), never stored.                                             |
| F4  | Deck puts money fields on `Property` (`askPrice`, `serviceCharge`, `expectedRent`, `yield`).                            | Money values are `Estimate` objects linked by `ESTIMATES` edges, so each carries confidence/source/asOf/dataKind/scenario. `yield` is derived. F2 in the deck ("estimate stub at 40% confidence") already implies this. |
| F5  | `Estimate.scenarioRef` is a reference, which conflicts with "edges are the only source".                                | Narrow, documented exception: `estimate_details.scenario_id` is a **qualifier** (which world the value belongs to), not a relationship. The UI still renders it as a graph link. It is the only such column.            |
| F6  | `assignee` and `ownerRef` point at `Person`, but no edge type means "assigned to".                                      | `REFERENCES` edges with a `label` (`assignee`, `owner`).                                                                                                                                                                |
| F7  | Slip needs a baseline. The deck has `slipDays` (derived) but nothing to derive from.                                    | Milestones store `baseline_date` alongside `date`. Slip = scheduled − baseline, derived.                                                                                                                                |
